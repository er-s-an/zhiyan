# 知研台 V2 PRD：全球 OPC 与知乎知识出海

- 版本：V2.0（知乎黑客松 S3 比赛版）
- 日期：2026-11-12
- 主报赛道：AI×出海
- 能力底色：AI×知识与探索
- 当前代码基线：用户提供的 `86ea50b` 状态说明
- 本文作用：统一新方向、现有能力迁移方式、P0 范围、页面改造、验收标准与演示动线

## 1. 为什么改版

V1 已经具备研究设计确认、知乎接口调用、样本工作台、编码、质检、导出和示例缓存，但产品叙事仍偏“中文研究工具”，检索主要是预先设计好的固定查询，LLM 只承担翻译，尚未充分体现新方向的两项核心价值：

1. **知乎知识出海**：把海外用户难以系统获取的中文公开讨论，转化为可复核的英文研究证据。
2. **OPC 的研究部**：帮助缺少专职研究团队的一人公司和小团队，在开发前理解真实用户场景、发现未知问题、检查产品假设。

V2 不重做一个“更大的研究平台”，而是把现有能力串成一条更适合比赛演示的主线：

> 英文产品决策 → 中文研究计划 → 适应性知乎检索 → 可接管证据分析 → 双语决策简报 → 下一步验证。

## 2. 产品定义

### 2.1 一句话定位

**知研台是面向全球 OPC、小团队和产品决策者的 AI 研究工作台，把知乎公开讨论转化为可复核、双语的市场与产品研究证据。**

中文口号：

> 让一个人也能拥有一支懂中国用户的研究团队。

英文表达：

> A research team for global builders, built on real Zhihu conversations.

### 2.2 赛道叙事

产品同时具有三层“出海”含义：

- **产品出海**：英文优先、面向全球用户，不是只服务中文用户的站内工具。
- **知识出海**：把知乎中文公开讨论转化为全球团队可以理解和使用的研究证据。
- **决策出海／入华**：海外团队进入中国前理解本地用户，全球 OPC 做产品时获得中文用户研究能力。

主报 AI×出海时，不应只讲“帮助海外企业入华”，必须同时讲清产品自身的全球用户和英文交付。

### 2.3 与通用 AI 的差别

通用 AI 可以读取部分公开网页，也可能搜到部分知乎内容，因此产品不得宣称“其他 AI 完全看不到知乎”。

真正的差别是：

- 通用 AI 读到哪些网页、覆盖哪些讨论，通常不可控；
- 知研台通过知乎官方能力，按研究计划进行多轮检索；
- 知研台记录查询目的、词汇来源、样本纳入排除和证据缺口；
- 知研台保留场景、条件、替代方案、分歧和反例，而非压成统一答案；
- 知研台最终服务产品决策和下一步验证，不只生成一段回答。

一句话对照：

> 通用 AI 是在网上找资料后回答；知研台是在知乎里执行一次可检查的用户研究。

## 3. 目标用户与核心场景

### 3.1 主用户

**缺少专职研究团队的产品决策者**：OPC、独立开发者、小团队创始人、产品经理和独立顾问。

他们共同的问题不是“完全不会搜索”，而是：

- 不知道中国用户的原生表达和真实讨论入口；
- 不知道自己应该搜索哪些词；
- 没有时间阅读大量长讨论；
- 容易只找到支持原有想法的材料；
- 得到报告后仍不知道下一步验证什么。

### 3.2 P0 主场景：Product Discovery

用于判断“什么值得做、为谁做、暂时不该做什么”。

输出包括：

- 目标人群与使用场景；
- 用户当前任务和遇到的问题；
- 现有替代方案及不满；
- 用户原生的表达与关注角度；
- 分歧、反例和证据缺口；
- 对产品假设的影响；
- 下一步最便宜的验证。

### 3.3 次级场景：China Entry Research

用于海外团队进入中国市场前的探索，复用同一个研究引擎，仅更换研究简报模板。

P0 不单独开发完整入华研究协议，不输出市场规模、法律合规结论或购买率。比赛案例可以同时体现“海外 OPC 为中国用户做产品”，从而覆盖两个场景。

### 3.4 比赛主案例

> 一个海外 OPC 准备为中国自由职业者开发 AI 合同与回款工具，希望理解报价、反复改需求、验收和拖款问题，再决定是否投入开发。

该案例必须能展示关键词扩展：从产品词“AI 合同工具”，逐步发现“接单、私活、约稿、外包、甲方、定金、尾款、验收、需求变更”等真实讨论入口。最终关键词以真实检索结果为准，不预写成结论。

## 4. 产品原则

1. **公开证据，不出售用户数据**：只使用规则允许的公开内容和官方接口能力，保留作者、出处和原文链接。
2. **研究先于搜索**：先明确决策、研究问题和边界，再允许执行查询。
3. **关键词在检索中生长**：不要求用户或模型一开始列全关键词，而是从真实讨论中逐步发现。
4. **保留分歧**：开放问题的不同观点本身就是研究价值，不强行形成统一口径。
5. **样本不是市场统计**：知乎讨论可支持定性探索，不直接证明市场规模、购买率、因果或整体人群分布。
6. **AI 提议，证据约束**：LLM 可以扩展查询和辅助编码，但结论必须回到样本，计数与统计由确定性逻辑完成。
7. **用户可以接管**：用户能修改计划、补充关键词、排除样本、调整编码，并看到报告同步变化。
8. **报告不是终点**：每次研究必须落到“对决策有什么影响、下一步验证什么”。

## 5. P0 用户流程

### 5.1 创建研究

用户可用英文或中文输入：

- 正在考虑的产品或决策；
- 目标用户和市场；
- 已有什么假设；
- 最担心判断错在哪里。

系统生成结构化 Brief，并让用户确认。缺字段时可以追问，但比赛演示不得陷入过长问答。

### 5.2 方法适用闸门

执行前输出三类判断：

- **适合知乎探索**：用户经验、使用场景、产品评价、替代方案、争议和反对理由；
- **需要其他数据补充**：付费意愿、企业采购、市场规模、地区差异等；
- **不能由知乎单独证明**：统计比例、法律合规、因果关系和整体市场结论。

闸门必须影响最终报告可用措辞，不能只显示一条提示后继续输出过强结论。

### 5.3 研究设计确认

沿用现有确认门，新增展示：

- 决策问题；
- 研究问题与待验证假设；
- 初始查询矩阵；
- 样本纳入排除标准；
- 反例检索方向；
- 查询和时间预算；
- 预计交付物。

用户确认后才可调用知乎；继续保留设计外查询拒绝，但“经系统扩展并写入研究计划的后续查询”属于合法计划更新，必须保留版本和原因。

### 5.4 适应性检索

执行以下循环：

> 种子查询 → 获取候选 → 阅读与筛选 → 提取新词汇和角度 → 更新覆盖图 → 选择下一查询 → 达到停止条件。

P0 默认预算：

- 初始 4–6 个不同维度的种子查询；
- 最多 2 轮扩展，每轮选择 2–4 个查询；
- 单次研究总查询数默认不超过 12；
- 候选来源默认不超过 60 条，纳入样本按质量而非数量决定；
- 缓存案例用于完整演示，现场保留轻量真实检索路径。

以上数字是可配置默认值，不是研究质量指标。

### 5.5 证据工作台

沿用现有样本筛选、搜索、纳入理由、编码修改、搁置恢复和即时重算，新增：

- 该样本由哪一轮、哪条查询发现；
- 查询为了解决哪个覆盖缺口；
- 样本对应的人群、场景、立场和替代方案；
- 原文摘录与英文翻译并排；
- 原帖链接和作者信息；
- 该样本支撑或反驳哪些发现。

### 5.6 语义分析与反例

P0 输出六类发现：

1. 人群与场景；
2. 用户任务与痛点；
3. 当前替代方案；
4. 选择理由与不满；
5. 分歧与反例；
6. 未知问题与证据缺口。

每条发现区分：

- **原文直接表达**；
- **多样本支持的归纳**；
- **AI 对产品的推断**。

每个归纳必须挂接证据；没有足够证据时标记为假设，不进入“关键结论”。

### 5.7 双语决策简报

最终交付控制在短报告内：

1. 本次研究服务什么决策；
2. 关键发现；
3. 用户场景与替代方案；
4. 分歧、反例和意外发现；
5. 中文原话、英文翻译和原文链接；
6. 本次不能证明什么；
7. 对产品选项的影响；
8. 下一步验证及证伪条件。

英文和中文版本从同一份结构化研究生成，不允许分别生成导致结论不一致。

### 5.8 下一步验证

系统至少生成：

- 优先访谈的 2–3 类对象；
- 5–8 个访谈问题；
- 一个最低成本验证动作；
- 明确证伪条件：出现什么结果时，应放弃或修改当前产品假设。

P0 不实现自动招募、自动访谈或问卷投放。

## 6. 核心能力：适应性查询与词汇发现

### 6.1 初始查询不是同义词列表

研究计划至少覆盖以下维度中的四类：

| 维度 | 作用 | 示例，仅作查询设计参考 |
|---|---|---|
| 人群 | 找到不同身份的自我表达 | 自由职业者、独立开发者、设计师、顾问 |
| 场景 | 找到问题发生的具体环节 | 接单、报价、交付、验收、回款 |
| 任务 | 找到用户试图完成的事情 | 怎么报价、如何拒绝修改、是否收定金 |
| 症状 | 找到用户的原生问题表达 | 改需求、拖款、压价、跑单、扯皮 |
| 替代方案 | 找到当前解决方式 | 模板、电子签、熟人合作、平台担保 |
| 评价与立场 | 找到支持、反对和条件性判断 | 靠谱、没必要、后悔、推荐、不适合 |

不得将所有词做笛卡尔积后无差别请求。初始查询应选择最可能发现真实讨论的组合。

### 6.2 新词必须来自证据

每轮检索后，LLM 从候选样本中提取“查询扩展建议”，每条建议至少包含：

- 新词或新表达；
- 来源样本 ID；
- 来源原句或合理摘要；
- 它代表的新人群、新场景、新任务、新替代方案或新立场；
- 建议的下一条查询；
- 预计补齐的覆盖缺口。

禁止把模型凭空想到但未在样本中出现的词，伪装成“知乎用户正在使用的表达”。模型先验可以用于生成初始种子查询，后续发现的词必须标明来源。

### 6.3 覆盖图驱动下一搜

P0 维护一张轻量覆盖表：

- 人群：发现了谁，还缺谁；
- 场景：覆盖哪些任务环节；
- 立场：支持、反对、条件性评价是否均衡；
- 替代方案：是否只看到了用户抱怨，没看到现有解决方式；
- 时间：样本是否超出研究时间窗，近期证据是否不足；
- 重复：新查询是否仍主要返回同一批内容。

下一轮的每条查询都必须有目的，例如“补咨询顾问人群”“寻找合同无效的反例”“寻找平台担保替代方案”，而不是“再搜一些相关资料”。

### 6.4 反例检索

研究计划确认时即加入反例方向；执行中如果某主题证据明显单向，系统应追加：

- 满意或正面经历；
- 问题并不存在的情况；
- 现有方案已经足够的情况；
- 产品或方法失效的条件；
- 与当前产品假设相反的使用方式。

反例不足时可以披露“未找到足够反例”，不得伪造平衡。

### 6.5 停止规则

满足任一条件即可停止：

- 连续两轮没有出现新的重要主题；
- 主要研究维度已覆盖，继续查询只增加重复证据；
- 达到查询、候选样本或时间预算；
- 官方接口没有足够结果，记录证据缺口后停止扩展。

界面统一表述为“本次预算内主题趋于稳定”或“达到研究预算”，不得宣称“已穷尽知乎”或“样本具有统计代表性”。

### 6.6 研究词表是正式交付物

报告和研究过程均展示：

- 用户最初提供的词；
- 从真实讨论中发现的词；
- 每个新词的来源；
- 哪些新词带来了新主题；
- 哪些查询没有有效结果；
- 仍可能遗漏的方向。

这部分是比赛中的核心“哇时刻”：**系统不仅回答用户的问题，还帮助用户发现原本不知道应该搜索什么。**

## 7. LLM 与确定性逻辑的新分工

V1 的“LLM 只做翻译”不再足以支撑 V2，但也不需要让 LLM 直接控制全部研究。

### 7.1 LLM 负责

- 将用户 Brief 拆为研究问题和初始查询建议；
- 从真实样本中提议新词、新场景和新角度；
- 辅助开放编码和主题命名；
- 提议反例查询；
- 生成中英双语摘录和结构化报告草稿；
- 根据已确认发现生成下一步访谈建议。

### 7.2 确定性逻辑负责

- 查询白名单、预算和版本校验；
- 样本去重、筛选状态和来源关系；
- 编码与样本的多对多关联；
- 数量、比例和时间窗统计；
- 发现所挂证据的完整性检查；
- 样本修改后的分析与报告重算；
- 导出和分享。

### 7.3 人工负责

- 确认研究设计；
- 增补或否决查询方向；
- 排除不可靠样本；
- 修改主题和编码；
- 判断 AI 推断是否可接受；
- 做最终产品决策。

LLM 的每次查询扩展和编码建议都要结构化保存，出现错误时可回退到上一版本，不直接污染唯一事实源。

## 8. 页面改造

### 8.1 首页工作台

保留知乎蓝白、刘看山 IP、最近记录和示例库。

改动：

- 从“中文优先”改为中文／英文可切换，默认根据浏览器语言显示；
- 首屏只突出一个动作：“开始一次产品研究”；
- 输入框以决策为导向，不再只问研究主题；
- 增加一句价值说明：把知乎真实讨论变成双语产品研究证据；
- 主示例替换为海外 OPC 研究中国自由职业者案例，其余案例作为辅助。

### 8.2 研究设计页

保留协议编辑、执行前检查和确认门，新增：

- 方法适用闸门；
- 决策问题与产品假设；
- 初始查询矩阵；
- 反例方向；
- 查询预算；
- 研究计划版本记录。

### 8.3 当前研究页

在现有“协议／样本／分析／质检／交付”上增加“探索”视图，用于展示：

- 当前查询轮次；
- 查询目的和进度；
- 新发现词汇及来源；
- 覆盖图；
- 重复样本与证据缺口；
- 停止原因。

不另做复杂多 Agent 监控页，不向普通用户展示原始技术日志。

### 8.4 样本视图

保留现有交互，新增查询来源、人群、场景、立场、双语摘录和支撑／反驳关系。搁置样本后，相关发现、计数、双语报告必须同步更新。

### 8.5 分析视图

从关键词计数优先改为“发现优先”：

- 每个发现先显示含义和证据；
- 计数只作为样本描述，不作为市场需求强弱证明；
- 明确展示反例和 AI 推断；
- 支持用户修改主题名称、定义和编码。

### 8.6 质检视图

保留“可以支持／不能证明”，新增：

- 查询覆盖和停止原因；
- 新词来源是否完整；
- 关键发现是否都有证据；
- 是否存在只有单一立场的主题；
- 时间窗是否真正执行；
- 中英文结论是否一致；
- 是否出现样本无法支持的统计或商业化措辞。

### 8.7 交付视图

保留 Markdown、PDF 和复制能力，新增：

- 中文／英文切换；
- Decision Memo 短版；
- 完整证据附录；
- 下一步访谈提纲；
- 分享时保留作者、出处和知乎原文链接。

## 9. 现有能力迁移表

| 现有能力 | V2 处理 | 说明 |
|---|---|---|
| 知乎蓝白 UI、刘看山 IP、响应式布局 | 直接复用 | 主要改文案、语言和部分信息架构 |

## 12. 验收标准

### 12.1 主流程

1. 用户用英文提交主案例 Brief，系统生成中文研究计划，用户可编辑并确认。
2. 未经确认不调用知乎；设计外直接注入查询仍被拒绝。
3. 第一轮真实结果返回后，系统至少提出 3 个有来源样本的新词或新角度；若真实语料不足，不得为满足测试而伪造，应更换主案例。
4. 至少一个新词触发后续查询，并带来新的有效样本或新的证据缺口。
5. 每个后续查询都有目的，不属于简单同义词重复。
6. 系统至少执行一次反例查询，或明确展示未找到反例。
7. 达到停止条件后展示原因，不宣称穷尽知乎。

### 12.2 证据与分析

1. 每条关键发现至少挂接一条可打开的原始证据；重要归纳应尽量包含不同来源。
2. 原文、样本归纳和 AI 推断在 UI 上有明确区分。
3. 样本纳入排除、编码修改和搁置恢复后，计数、发现和报告一致重算。
4. 报告不出现由知乎样本直接推导的市场规模、购买率或整体人群比例。
5. 时间窗、营销内容和重复内容处理逻辑在真实样本上生效。
6. 至少展示一个反例、条件性观点或未解问题。

### 12.3 双语与导出

1. 中英文报告由同一结构化研究生成，关键发现数量、证据和限制一致。
2. 英文发现可展开中文原话和英文翻译，并跳回知乎原文。
3. Decision Memo 包含决策影响、不能证明的事项和下一步证伪条件。
4. Markdown／PDF 导出后链接、作者和出处不丢失。

### 12.4 工程与演示

1. 原有测试继续通过，新增查询扩展、计划版本、反例、双语一致性和报告重算测试。
2. 构建通过，无控制台错误，现有响应式标准不下降。
3. 完整缓存案例可离线演示；现场真实检索失败时可切换缓存，但必须明确标识，不伪装成实时结果。
4. 密钥继续只放环境变量，不进入仓库或导出文件。

## 13. 比赛演示动线

### 13.1 演示顺序

1. **先讲问题**：AI 让产品更容易做出来，但 OPC 仍靠猜决定做什么；中文知乎讨论又很难被海外团队系统使用。
2. **英文输入主案例**：海外 OPC 想为中国自由职业者做 AI 合同与回款工具。
3. **展示研究计划**：系统拆出中文人群、场景、问题和反例方向，并说明知乎不能证明付费率。
4. **展示词汇发现**：用户最初只提“合同工具”，系统从真实讨论中发现新的原生表达和研究角度。
5. **展示可接管**：排除一条营销或不可靠样本，相关发现即时变化。
6. **展示分歧**：同一问题存在不同条件和相反经历，不压成统一答案。
7. **展示英文交付**：英文发现、中文原话、原文链接和下一步访谈证伪条件。
8. **落到平台价值**：知研台让知乎内容成为中文知识出海和机构研究服务的新入口。

### 13.2 评委问答口径

**“我直接让 ChatGPT 搜知乎不也行？”**

> 它可以读到部分公开网页，但不会天然形成有预算、有覆盖目标、有反例、有纳入排除和可重算证据链的研究过程。知研台的差异不是模型会不会搜索，而是系统是否真的执行研究。

**“这不就是翻译和总结吗？”**

> 翻译只存在于交付层。核心过程是把英文决策拆成中文查询，从真实讨论发现新词，再用新词补齐覆盖和反例，最后让用户修改证据并重算结论。

**“这些讨论能代表中国市场吗？”**

> 不能，所以系统把知乎限定为定性探索证据，并在方法闸门和交付中阻止统计化结论。它帮助决定下一步验证什么，不代替市场统计。

**“知乎自己做怎么办？”**

> 知研台是在知乎官方能力上验证新的应用和商业化场景，目标是成为知乎知识出海和机构研究服务的应用样板，而不是绕过平台抓取内容。

## 14. 实施顺序

### 工作包 A：先锁主案例和叙事

- 确认主案例在知乎有足够真实讨论；
- 用现有接口手动跑一轮，验证能否发现多个原生表达和反例；
- 完成中英文首页文案、项目定位和演示脚本；
- 若主案例语料不足，先换案例，不在代码完成后硬救。

### 工作包 B：适应性检索

- 增加 QueryRun、VocabularyItem 和计划版本；
- 实现初始查询、样本驱动扩展、覆盖图和预算停止；
- 把扩展查询纳入确认与审计体系；
- 保留现有固定场景包作为回归测试。

### 工作包 C：语义发现与人工接管

- 增加 LLM 辅助编码和 Finding 结构；
- 保留确定性计数和即时重算；
- 接入反例、AI 推断和证据边界；
- 扩展现有样本工作台，不重写交互。

### 工作包 D：双语决策交付

- 统一中英文结构化报告源；
- 增加 Decision Memo、原话对照和下一步验证；
- 扩展 Markdown／PDF 导出和质检。

### 工作包 E：示例、测试与路演

- 生成真实主案例缓存和证据附录；
- 完成端到端与异常路径测试；
- 完整案例离线演示，轻量真实现场检索；
- 更新 README、产品说明和 decisions 记录。

实施优先级为 **A → B → C → D → E**。不要先做完整英文报告再补检索，也不要先加复杂研究资产库。

## 15. 文档与 Git 管理建议

- 新增本 V2 PRD，旧 PRD 和 Pre-build 方案保留为历史，不在多个文档里同时维护冲突的“当前方向”。
- README 和产品说明只保留新定位，并链接本 PRD。
- `decisions.tsv` 追加方向变更：全球 OPC、知乎知识出海、适应性检索、LLM 辅助编码、双语 Decision Memo。
- 不删除已有测试和示例；主案例替换不等于清空旧资产。
- 每个工作包单独提交，避免把 UI、检索、编码和报告改造混成一个无法回退的大提交。

## 16. 最终收敛

V2 的竞争力不由功能数量证明，而由下面这条真实可运行的证据链证明：

> 用户只提供一个产品决策，知研台能够从知乎真实讨论中发现他没想到的原生词汇和研究角度，补齐证据与反例，让他检查并修改研究过程，最后得到一份中英一致、知道边界、能指导下一步行动的简报。

比赛版只要这条链足够顺，就已经同时回答了：

- 为什么是知乎；
- 为什么是 AI 出海；
- 为什么适合 OPC；
- 为什么不是通用 AI 搜索；
- 为什么值得知乎继续孵化。
