# 下一步行动方案：从「调研报告」到「Pre-build 决策冲刺」

> 版本：2026-11-12
> 适用：知研台当前版本（GitHub `62999dd`）之后的下一轮迭代
> 结论先行：**不再扩功能菜单。下一版只做一件事——把「知乎公开讨论」推进到「一个人也能用的建/不建决策」。**
>
> **完成状态（2026-11-12）**：本文档已完成；本轮只提交文档，没有改产品行为。下一步从 P0-1（决策契约 + 方法适用闸门）开始，需你确认后再动代码。

---

## 0. 现在到底做什么

一句话：

> **做「Pre-build 决策冲刺」：用户带着一个产品想法来，30–60 分钟内拿到一份 Decision Memo——建议做/改/停/先验证，依据是什么，什么情况下该停，下一步最便宜的验证是什么。**

这一版不追求「研究功能齐全」，只追求：

1. **不问错问题**：方法适用闸门先挡住「用中文知乎判断北美市场」这类错误。
2. **不假装有结论**：数据不匹配时，只输出假设，不输出强建议。
3. **分析能被审查**：LLM 辅助开放编码 + 代码本版本 + 人工复核 + 负案例 + 敏感性分析，最终统计由确定性程序生成。
4. **交付能行动**：Decision Memo 给出建议、置信度、kill criteria、下一步实验。
5. **两种人看同一套东西**：创始人看结论与行动；研究员打开「方法视图」看证据与过程。

## 1. 先冻结：这轮明确不做

以下全部推迟，不要在这轮碰：

- TAM / SAM / SOM、市场规模模型
- MaxDiff / conjoint / Van Westendorp / Kano 问卷
- 小红书、抖音、Amazon、App Store 等八平台接入
- 企业 SSO、权限、审计、团队协作
- 完整访谈招募 / 问卷系统 / 实验平台
- 继续堆 UI 页面和动画

理由：这些不是当前最短的板。当前最短的板是——

> **从「搜到的 20 条知乎内容」到「这个产品该不该做」之间，分析是否成立。**

## 2. 产品主线：一条闭环

```
产品想法
  ↓
① 决策契约（Decision Contract）
   决策是什么、谁来决定、可逆性、失败成本、证据门槛、kill criteria
  ↓
② 方法适用闸门（Method-fit Gate）
   目标人群 vs 数据人群、决策类型 vs 证据类型
   不匹配 → 只允许「假设」，不允许「强建议」
  ↓
③ 适应性证据收集（Adaptive Evidence）
   动态扩展查询、覆盖矩阵、纳入/排除执行、时间窗执行、饱和/停止规则、敏感性分析
  ↓
④ 可审计的语义编码（Auditable Coding）
   LLM 开放编码 + 引用 span + 代码本版本 + 人工复核/双编码 + 负案例
  ↓
⑤ Decision Memo
   建议（做/改/停/先验证）+ 置信度 + 依据 + 反证 + kill criteria + 下一步最便宜验证
  ↓
⑥ 结果回收 & 决策记录
   实验/访谈结果回来后，更新结论；记录采纳/不采纳
```

**这一版的成功标准不是「报告更漂亮」，而是：用户看完能做一个更便宜、更可逆的下一步决定。**

## 3. 下一版 MVP（P0）：五个工作包

### P0-1 决策契约 + 方法适用闸门

**为什么先做**：如果问题问错了，后面 sampling / coding 再专业也没用。

**产品表现**：

- 新建研究的第一步不是「写简报」，而是 6 个问题：
  1. 你要做什么决定？
  2. 谁做这个决定、什么时候要？
  3. 这个决定可逆吗？做错的成本大概是多少？
  4. 你愿意为验证花多少时间/钱？
  5. 什么结果会让你继续、修改或停止？
  6. 目标市场/人群是谁？
- 系统根据答案给出「证据门槛」和「推荐研究层级」。
- 方法闸门检查：
  - 目标市场 vs 知乎可观察人群是否匹配（语言/地域/平台/时间）；
  - 决策类型（探索/选择/估算/验证）vs 当前数据能提供的证据类型（态度/行为/量化）；
  - 可逆性/失败成本 vs 证据门槛。
- 输出三种状态：
  - `fit`：可以给方向性建议；
  - `partial`：只能给假设 + 下一步验证；
  - `mismatch`：禁止强结论，只能给「该问什么 + 该用什么方法」。

**验收**：

- 输入「北美户外储能」+ 数据源「中文知乎」→ 必须判 `mismatch`，不输出「北美用户需要 X」。
- 输入「多猫喂食器」+ 数据源「知乎」→ 判 `fit` 或 `partial`，允许方向性建议。
- 输入「企业采购 AI 会议纪要」+ 数据源「知乎个人发帖」→ 判 `partial/mismatch`，提示需要 win/loss 或内部数据。
- 闸门结果在 UI 上可见，不能只写在报告最后一页。

### P0-2 真正的适应性抽样

**为什么**：固定 4 条查询 × 前 5 条 = 搜索排序收集，不是抽样。

**产品表现**：

- 从「固定查询列表」改为「种子查询 + 覆盖矩阵 + 动态扩展」：
  - 覆盖维度：场景 × 角色 × 时间桶 × 来源；
  - 每轮检索后计算覆盖缺口；
  - 针对缺口生成下一轮查询（包括反证查询，如「为什么不买/后悔/劝退」）；
  - 达到覆盖目标或饱和阈值就停，并记录「为什么停」。
- 纳入/排除规则真正执行：
  - 时间窗外的帖子：默认不进入发现，或进入「敏感性分析」对照组；
  - 营销/重复/二手：标记 + 可配置是否剔除；
  - 同一作者多帖：做作者级去重或降权。
- 敏感性分析：去掉营销、过时、单一来源后，主要结论是否仍成立；在 UI 中显示「稳健 / 不稳健」。

**验收**：

- 每次研究都有 `samplePlan` 与 `stopReason`，可解释「为什么继续、为什么停」。
- 覆盖矩阵至少包含场景/角色/时间三类缺口。
- 报告显示敏感性分析结果，而不是只显示「本样本计数」。

### P0-3 可审计的语义编码

**为什么**：关键词计数不是主题分析；确定性只能保证复算，不能保证理解。

**产品表现**：

- LLM 开放编码：
  - 每条内容输出：编码、引用 span（原文片段）、理由、置信度；
  - 先开放编码，再归纳成代码本；代码本有版本号与变更记录。
- 人工复核：
  - 研究员可以接受/修改/拒绝每个编码；
  - 至少 10–20% 样本双编码，计算一致率（目标：Cohen's kappa ≥ 0.6 或一致率 ≥ 80%，以实际数据为准）；
  - 记录分歧与裁决。
- 负案例：
  - 主动搜索与主结论相反的内容；
  - 在 Decision Memo 中显示「哪些证据反对我们的判断」。
- 确定性收口：
  - 最终计数、主题分布、报告文本由代码基于「已复核编码」生成；
  - LLM 不直接写最终结论。

**验收**：

- 每个编码可下钻到原文 span 与理由。
- 代码本有版本号和变更记录。
- 报告披露：编码由谁/什么模型完成、人工复核比例、一致率、AI 使用方式。
- 去掉 LLM 编码后，确定性统计仍可复算。

### P0-4 Decision Memo（决策转化层）

**为什么**：现在的「发现」是「N 条提到 X」，不是「所以该做什么」。

**产品表现**：一页纸，固定结构：

```
建议：build / reshape / park / kill / validate_first
置信度：低 / 中 / 高（说明理由）
最强证据：3 条（带原文链接）
反证/负案例：1–3 条
关键假设：...
Kill criteria：出现什么信号就停止
下一步最便宜验证：找谁、问什么、测哪两个价值主张、预计耗时/成本
暂时不要做：...
方法适用性 & AI 披露
```

**验收**：

- 每条建议必须绑定证据与反证，不能只有结论。
- 置信度为「低」时，不能输出「build」强建议。
- Memo 能导出为 Markdown/PDF，能贴进 PRD/评审会。

### P0-5 双层工作台（结论视图 / 方法视图）

**为什么**：一人公司要简单；专业研究员要能接管。

**产品表现**：

- **结论视图（默认）**：Decision Memo + 下一步 + 关键依据；隐藏方法论细节。
- **方法视图（一键展开）**：决策契约、闸门结果、RQ/假设、抽样计划、覆盖矩阵、代码本版本、编码 trace、人工复核、负案例、敏感性、AI 披露。
- 不是两个产品、两套后端；是同一套数据的 progressive disclosure。

**验收**：

- 创始人 3 分钟内能读懂建议与下一步。
- 研究员能在 5 分钟内找到每个结论的证据链。
- 两个视图数据完全一致。

## 4. 数据模型：先加这些字段

```ts
type DecisionType = "explore" | "choose" | "validate" | "estimate";
type Reversibility = "cheap" | "moderate" | "expensive";
type EvidenceTier = "L0_public_ugc" | "L1_light_validation" | "L2_structured" | "L3_decision_grade";
type Fit = "fit" | "partial" | "mismatch";
type Recommendation = "build" | "reshape" | "park" | "kill" | "validate_first";

interface DecisionContract {
  decision: string;
  decisionMaker: string;
  deadline: string;
  reversibility: Reversibility;
  failureCost: string;
  evidenceBar: string;
  killCriteria: string[];
  successCriteria: string[];
  targetMarket: string;
  targetPopulation: string;
}

interface MethodGate {
  decisionType: DecisionType;
  requiredEvidence: string[];
  availableData: string[];
  populationMatch: Fit;
  reasons: string[];
  allowedOutput: "strong_recommendation" | "directional" | "hypotheses_only";
  recommendedTier: EvidenceTier;
  nextMethod?: string;
}

interface ResearchQuestion {
  id: string;
  question: string;
  hypothesis: string;
  disconfirmingEvidence: string;
  sceneIds: string[];
  codeIds: string[];
}

interface SamplePlan {
  targetN: number;
  quotas: { dimension: string; value: string; min: number }[];
  saturationRule: string;
  maxQueries: number;
  expansionPolicy: string;
  sensitivityChecks: string[];
}

interface CodingTrace {
  itemId: string;
  codeId: string;
  span: string;
  rationale: string;
  confidence: "low" | "medium" | "high";
  model: string;
  promptVersion: string;
  reviewStatus: "pending" | "accepted" | "edited" | "rejected";
  reviewedBy?: string;
}

interface CodebookVersion {
  version: string;
  createdAt: string;
  codes: string[];
  changes: string;
}

interface DecisionMemo {
  recommendation: Recommendation;
  confidence: "low" | "medium" | "high";
  confidenceReason: string;
  evidence: { text: string; itemIds: string[] }[];
  disconfirming: { text: string; itemIds: string[] }[];
  assumptions: string[];
  killCriteria: string[];
  nextTest: {
    method: string;
    who: string;
    questions: string[];
    successCriteria: string;
    estimatedCost: string;
  };
  doNotDo: string[];
  disclosure: string;
}
```

## 7. 5 分钟 Demo 脚本（建议）

1. **0:00–0:40 定位**：一人公司/小团队不缺「更多信息」，缺「建/不建判断」；知研台是 pre-build 决策冲刺。
2. **0:40–1:30 错误问题**：输入「北美户外储能独立站」；闸门提示「中文知乎 ≠ 北美用户」；系统只给假设 + 下一步（访谈/落地页），不硬给市场结论。
3. **1:30–2:30 正确问题**：切到「多猫家庭智能喂食器」；展示决策契约、证据门槛、允许输出级别。
4. **2:30–3:40 证据**：展示适应性抽样（为什么继续/停止）、覆盖矩阵、一条编码的 quote span + 人工复核 + 负案例。
5. **3:40–4:30 Decision Memo**：建议（例如 reshape）、置信度、kill criteria、下一步最便宜验证。
6. **4:30–5:00 方法视图**：打开引擎盖，展示抽样/编码/披露；收尾「专业研究员可完整接管」。

## 8. 用户验证：这周就做，不要等产品完美

目标：10–20 个一人公司/独立开发者/小团队；先找 5 个。

访谈问题（不要问「你会不会用」）：

1. 你最近一次「做了才发现不值得做」的产品决定是什么？当时花了多久/多少钱？
2. 在那之前你做了什么研究？搜索、问人、还是直接做？
3. 你当时最想确认的是什么？什么信息会让你停？
4. 如果有一个工具在 30 分钟内给你一份「做/改/停 + 下一步验证」的 memo，你会用吗？会在什么节点用？
5. 你愿意为一次这样的决策冲刺付多少钱？还是更愿意订阅？
6. 你最不信任 AI 调研的地方是什么？（记录原话）

成功信号（qualitative，不装精确）：

- 5/10 能说出最近一次「做错」的决定；
- 5/10 说会在下一个项目开始前使用；
- 3/10 愿意预付一次 sprint；
- 至少 3 个人主动问「能不能现在就试」。

如果拿不到这些信号，先别扩功能，先改定位/人群。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| LLM 编码看起来深但不可靠 | 代码本版本 + quote span + 人工复核 + 一致率 + 负案例 + golden set |
| 闸门太硬，用户绕过 | 不只说「不行」，要说「现在能得出什么 + 下一步最低成本方法」 |
| Decision Memo 变成「AI 瞎建议」 | 建议必须绑定证据/反证；低置信度禁止强建议；人工最终决定 |
| 一人公司不愿付费 | 先卖「一次 sprint」，用 5 个设计伙伴验证；不先做订阅 |
| 范围蔓延回「功能平台」 | 用「一次冲刺只回答一个决策」约束范围；TAM/conjoint/SSO 全部推迟 |
| 数据/平台合规 | 公开内容 + 原链接 + 不复制全文；作者匿名化选项；保留期限 |
| 时间不够 | 先做 P0-1/2/4；P0-3 可先用「LLM 编码 + 人工抽检 10%」的简化版 |
